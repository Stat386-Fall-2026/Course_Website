Collaborating with Git and GitHub

Issues, Branches, Pull Requests, and Merge Conflicts

STAT 386

Today’s question

How can several contributors change one project without losing control of main?

By the end of this sequence, you should be able to:

  • Connect issues, branches, commits, pull requests, reviews, and merges
  • Review a proposed change before it enters main
  • Create and resolve a simple merge conflict
  • Apply the same workflow to human and AI collaborators

Suggested time: 2 minutes.

This deck is designed as one continuous sequence. It has a natural stopping point after the second pull request example, immediately before the merge conflict section.

Two collaborators, one file

You and a collaborator both clone the same repository.

You each change this line:

SUMMARY_METRICS = ["mean"]

Your collaborator’s work reaches main first.

What happens to your change? What should happen next?

Suggested time: 3 to 5 minutes.

Give students 30 seconds to think alone, then one minute with a partner. Collect predictions without correcting them yet. Listen for assumptions that Git combines everything automatically, overwrites one version, or blocks both people from working.

Collaboration requires more than shared access

A team needs answers to four questions:

Question GitHub feature
What work needs attention? Issue
Where can I work safely? Branch
What change am I proposing? Pull request
Should this enter main? Review and merge

Shared access lets people edit. A collaboration process helps them coordinate.

Suggested time: 2 minutes.

Return to the opening scenario. Both people had access, but access alone did not establish who was doing what or how the changes should be evaluated.

The collaboration cycle

Each stage preserves context for the next person who must understand the work.

Suggested time: 2 minutes.

Build the cycle from left to right. Ask students which stages happen in Git and which depend on GitHub. Branches, commits, and merges are Git concepts. Issues, pull request pages, and review tools are GitHub collaboration features.

Source: https://docs.github.com/en/pull-requests/reference/pull-requests

Each stage answers a question

Stage Question it answers Evidence it preserves
Issue What outcome do we need? Description and acceptance criteria
Branch Where will this work develop? An isolated line of history
Commits What changed along the way? Focused project snapshots
Pull request What would this add to main? Diff, discussion, and checks
Review Does the proposal satisfy the issue? Comments and review decision
Merge Should the shared project adopt it? Integrated history

Suggested time: 3 minutes.

Do not treat the table as vocabulary to memorize. Choose one row at a time and connect it to the opening scenario.

Before anyone creates a branch

An issue says:

Improve the summary function.

What is still unclear?

  • What should the function return?
  • Which inputs must it handle?
  • What would count as complete?

Which questions must the team answer before anyone edits code?

Suggested time: 4 minutes.

Have students discuss with a neighbor before collecting answers. The point is not to produce one perfect issue. The point is to notice that a vague task gives the author and reviewer no shared standard for success.

Use their answers to motivate issue descriptions and acceptance criteria on the next slide.

Issues record future work

An issue can capture:

  • The outcome someone wants
  • The reason the work matters
  • Specific requirements or acceptance criteria
  • Discussion, assignments, labels, and links

What would another person need before they could begin this task?

Suggested time: 3 minutes.

Open an issue from the demonstration repository. Show the title, body, assignee, labels, and project field in the real GitHub interface. Avoid turning the slide into a tour of every sidebar control.

Source: https://docs.github.com/en/issues/tracking-your-work-with-issues/about-issues

GitHub Projects organize related work

A Project collects issues and pull requests into a shared planning view.

Backlog Ready In progress In review Done
Ideas worth considering Defined work Active branches Open pull requests Closed work

Projects can add:

  • Status, priority, dates, and custom fields
  • Table, board, and roadmap views
  • Workflows that update items as work changes

Issues describe individual work. Projects show how many work items fit together.

Suggested time: 4 minutes.

Show a real Project after discussing the concept. Add the demonstration issue to the Project and move it to In progress. GitHub Projects can track issues, pull requests, and draft ideas in several views.

Source: https://docs.github.com/en/issues/planning-and-tracking-with-projects Source: https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-built-in-automations

Branches isolate proposed work

A branch gives a set of commits a name.

git switch main
git pull
git switch -c issue-1-data-range
git status
  • Start from the current main
  • Use a name connected to the issue
  • Commit related work to the branch
  • Push the branch when others need to see it

Suggested time: 3 minutes.

Demonstrate the branch indicator in Positron and verify it with git status. Explain that git switch -c creates the branch and moves the working directory onto it. The branch begins at the current commit.

Source: https://docs.github.com/en/pull-requests/reference/branches Source: https://git-scm.com/docs/git-switch.html

Pull requests are proposals

A pull request compares a head branch with a base branch.

The proposal

  • Description of the intended change
  • Commits included in the branch
  • Files changed compared with main

The decision

  • Discuss the approach
  • Inspect the diff and checks
  • Approve, comment, or request changes
  • Merge only when the proposal is ready

Opening a pull request starts review. It does not make the proposal correct.

Suggested time: 3 minutes.

Emphasize the Files changed tab. GitHub describes pull requests as proposals to merge code changes, with discussion and review before merging.

Source: https://docs.github.com/en/pull-requests/reference/pull-requests

Review choices

Review action Use it when
Comment You have feedback or a question without a final decision
Approve The proposal satisfies the issue and is ready to merge
Request changes The author must revise the proposal before merging

A useful review points to evidence:

  • A requirement from the issue
  • A specific changed line
  • A test result or reproducible behavior

Suggested time: 3 minutes.

If possible, use a second course or TA account for the live review because authors cannot formally approve their own pull requests. A student volunteer with repository access can also submit the review while you guide the class.

Source: https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews

Example 1: a complete proposal

Issue 1: Add a data range helper

Add data_range(values) to stats_helpers.py.

Acceptance criteria

  • Return the difference between the largest and smallest values
  • Keep the function independent of external packages
  • Use a descriptive commit message

What evidence would convince you that the issue is complete?

Suggested time: 2 minutes to frame the example.

Before class, fork the prepared demonstration repository and run its Seed demo issue workflow. This creates this task as Issue #1 in the fork. Show the existing issue here, add it to the Project, and mark it In progress.

GitHub forks have their own issues, so Issue #1 is seeded in the fork rather than expected to copy from the upstream repository. Exact setup steps are in INSTRUCTOR_GUIDE.md.

Example 1: branch and implementation

git switch main
git pull
git switch -c issue-1-data-range

Paste into stats_helpers.py:

def data_range(values):
    return max(values) - min(values)

Then inspect the saved change in Positron.

Where does the change live before the commit?

Suggested time: 4 minutes.

Keep the code ready to copy. The coding should take seconds. Open the Source Control view, inspect the diff, and ask students to locate the branch name. Use git status in the terminal to verify the interface.

Example 1: commit, push, and propose

git add stats_helpers.py
git commit -m "Add data range helper"
git push -u origin issue-1-data-range

Open the pull request on GitHub.

Suggested description:

Fixes #1

Adds `data_range(values)` to calculate the
difference between the maximum and minimum.

Suggested time: 4 minutes.

Pause after each command. Ask whether the branch and commit are local, remote, or both. Explain that the -u option connects the local branch with its remote tracking branch. Show how the PR selects main as the base and issue-1-data-range as the head.

Source: https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue

Example 1: review, merge, and synchronize

On GitHub:

  1. Compare the issue with the PR description
  2. Inspect Files changed
  3. Approve the proposal
  4. Merge the pull request
  5. Confirm that the issue closes

Back in Positron:

git switch main
git pull
git log --oneline -3

Suggested time: 4 minutes.

Use a second reviewer if available. After merging, return to the Project and show the item moving to Done if the Project workflow is configured. Delete the remote feature branch if that matches the course workflow.

Where does the work live now?

After the pull request merges:

Location Contains the new function?
GitHub main Yes
Local main before git pull No
Local main after git pull Yes
Original feature branch Yes

Why does merging on GitHub leave the local repository unchanged?

Suggested time: 3 minutes.

This reconnects collaboration to the four-location model from Days 1 and 2. GitHub cannot silently rewrite the student’s local repository. Pull brings the remote commits into the local repository.

Example 2: a proposal that needs revision

Issue 2: Add a safe average helper

Add average_or_none(values) to stats_helpers.py.

Acceptance criteria

  • Return the arithmetic mean for a nonempty collection
  • Return None when the collection is empty
  • Keep the function independent of external packages

Suggested time: 2 minutes.

Create this issue live by copying the prepared title and body from demo_materials/issue-2-safe-average.md. This gives students one example of creating an issue after seeing the seeded issue. Add it to the Project and ask them to tell you the next step at each point in this example.

Example 2: the first proposal

def average_or_none(values):
    return sum(values) / len(values)

Use the same workflow:

git switch main
git pull
git switch -c issue-2-safe-average
git add stats_helpers.py
git commit -m "Add average helper"
git push -u origin issue-2-safe-average

Open the pull request with Fixes #2 in its description.

Suggested time: 4 minutes.

Paste the function, inspect the diff, commit, push, and open the pull request. Move briskly because the class already knows the sequence.

Does this proposal satisfy the issue?

def average_or_none(values):
    return sum(values) / len(values)

Test these two cases mentally:

average_or_none([2, 4, 9])
average_or_none([])

Should the reviewer approve, comment, or request changes?

Suggested time: 3 to 5 minutes.

Give students time to identify the division by zero. Ask them to connect the failure to the second acceptance criterion rather than merely stating that the code looks wrong.

Review changes the proposal

The reviewer requests the missing empty case.

Revised implementation:

def average_or_none(values):
    if not values:
        return None

    return sum(values) / len(values)

Commit and push the revision to the same branch.

Suggested time: 4 minutes.

Submit a Request changes review from the reviewer account. Revise the function in Positron, inspect the new diff, commit, and push. A comment works if a second reviewer account is unavailable, but explain the formal review choices.

One branch, one evolving proposal

The existing pull request updates when the branch receives another commit.

Review again:

  • Does the new code satisfy every acceptance criterion?
  • Did the revision introduce unrelated changes?
  • Does the conversation explain why the code changed?

A pull request can improve through several rounds of feedback before anyone merges it.

Suggested time: 3 minutes.

Show the new commit and updated Files changed tab. Approve and merge only after the class verifies the empty case. Return to the Project briefly and show the completed work.

Source: https://docs.github.com/en/pull-requests/reference/pull-requests

The cycle after two examples

Which stage protects the project when the first implementation is incomplete?

Suggested time: 3 minutes.

The best answer is the process as a whole, with review as the explicit decision point. The issue supplies the criteria used during review.

When branches collide

Git can combine many changes automatically. Sometimes it needs a person to decide.

Suggested time: 2 minutes.

If this begins a new class meeting, ask students to recall the two pull request examples before advancing.

Two valid branches, one shared line

Both branches begin here:

SUMMARY_METRICS = ["mean"]

Branch A

SUMMARY_METRICS = ["mean", "median"]

Branch B

SUMMARY_METRICS = [
    "mean",
    "standard_deviation",
]

Suggested time: 3 minutes.

Both changes are reasonable. Ask whether either contributor should discard the other person’s goal.

What happens after Branch A merges?

  1. Both branches start from the same commit.
  2. Branch A and Branch B change the same line.
  3. The team merges Branch A into main.
  4. Branch B tries to incorporate the new main.

What information would Git need in order to choose the final line?

Suggested time: 3 to 5 minutes.

Ask students to predict before showing any commands. Git sees two competing replacements for the same original line. It cannot infer that the team wants all three metrics.

A merge conflict pauses the merge

A conflict means Git cannot combine the changes confidently.

Common cases include:

  • Two branches change the same lines differently
  • One branch deletes a file that another branch edits

Git preserves both versions and waits for a person to choose the final content.

The conflict protects both contributors’ work from an automatic guess.

Suggested time: 3 minutes.

Describe a conflict as a request for judgment rather than a failure. Git has already combined every nonconflicting change it can.

Source: https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/resolving-a-merge-conflict-using-the-command-line

Conflict markers show both versions

<<<<<<< HEAD
SUMMARY_METRICS = ["mean", "standard_deviation"]
=======
SUMMARY_METRICS = ["mean", "median"]
>>>>>>> main
Marker Meaning in this merge
<<<<<<< HEAD Current feature branch
======= Boundary between versions
>>>>>>> main Incoming changes from main

Suggested time: 3 minutes.

The meaning of current and incoming depends on which branch is checked out and what is being merged. Do not encourage students to memorize that current always means their personal work.

Live conflict: update the feature branch

Assume Branch A has merged into main.

git switch main
git pull

git switch add-standard-deviation
git merge main

Then inspect:

git status

What has Git completed? What still needs a decision?

Suggested time: 4 minutes.

Run each command in the actual repository. After git merge main stops, read the terminal message and git status aloud. Open Source Control in Positron and locate the conflicted file.

Source: https://git-scm.com/docs/git-merge.html

Conflict resolution in Positron

Use the merge editor or edit the file directly.

The intended final code:

SUMMARY_METRICS = [
    "mean",
    "median",
    "standard_deviation",
]

Before saving, verify:

  • The final code expresses both intentions
  • No conflict markers remain
  • The file still contains valid Python

Suggested time: 5 minutes.

Show Positron’s conflict controls, but emphasize that Accept Current, Accept Incoming, and Accept Both are shortcuts. None of them understands the team’s intent. Manually edit the result if the shortcuts produce poor code.

Finish or restart the resolution

After resolving:

git add analysis_config.py
git status
git commit -m "Resolve metric configuration conflict"
git push

If you need to abandon the merge before committing:

git merge --abort

Return to the pull request and confirm that GitHub can merge it.

Suggested time: 4 minutes.

Explain that git add now means “I resolved this file.” The commit records the resolution, and the push updates the open pull request. Demonstrate git merge –abort only as a recovery option, not as the normal workflow.

Source: https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/resolving-a-merge-conflict-using-the-command-line

Pair activity: create and resolve a conflict

Work with your assigned partner and shared repository.

Each person will:

  • Create a branch from the same main
  • Paste a different prepared change into the same line
  • Commit and push the branch
  • Open a pull request

Then the pair will merge one PR and resolve the conflict in the other.

Finish line: both changes appear in main, both PRs are merged, and both computers have a clean git status.

Suggested time: 2 minutes to introduce the activity.

Instructor preparation: create or assign one shared repository per pair. Each repository should contain analysis_config.py with SUMMARY_METRICS = [“mean”] on main. Both students need write access.

Activity round 1: create the conflict

Partner A

  1. Create add-median
  2. Add "median"
  3. Commit, push, and open a PR

Partner B

  1. Create add-standard-deviation
  2. Add "standard_deviation"
  3. Commit, push, and open a PR

Review and merge Partner A’s pull request first.

Both partners must create their branches before either pull request merges.

Suggested time: 8 to 12 minutes.

The short version supplies exact commands on the next reference slide. The standard version asks students to reconstruct the workflow from the two demonstrations. Circulate and confirm that both branches began from the same commit.

Activity round 2: resolve the conflict

Partner B updates the feature branch:

git switch main
git pull
git switch add-standard-deviation
git merge main

Together:

  1. Read git status
  2. Resolve analysis_config.py in Positron
  3. Stage and commit the resolution
  4. Push the branch
  5. Review and merge the updated PR

Suggested time: 10 to 15 minutes.

Require both partners to agree on the final code before staging. If students finish early, ask them to explain the merge commit and pull the completed main branch on both computers.

Activity verification

On both computers:

git switch main
git pull
git status
git log --oneline --graph --all -8

Check analysis_config.py:

SUMMARY_METRICS = [
    "mean",
    "median",
    "standard_deviation",
]

Explain to your partner where the conflict occurred and which commit records the resolution.

Suggested time: 4 minutes.

Use this slide as an accordion. If time is short, verify only the final file and clean status. If time remains, have pairs interpret the graph and locate the merge commit.

Merge conflict debrief

Discuss with your partner:

  • Why could Git not choose the final line?
  • What part of the resolution required human judgment?
  • Which commands changed files, history, and GitHub?
  • How could the team reduce unnecessary conflicts?

When does a conflict reveal a coordination problem? When is it simply normal parallel work?

Suggested time: 4 to 8 minutes.

Take two or three responses. Avoid implying that every conflict means someone made a mistake. Small branches, frequent updates, clear issues, and communication can reduce avoidable conflicts.

The same workflow with an AI collaborator

AI collaborator

  • Responds to an issue
  • Creates a branch and commits
  • Opens a pull request
  • Comments on or reviews a PR

Repository owner

  • Defines the requested outcome
  • Inspects the diff and evidence
  • Requests changes when needed
  • Resolves competing intentions
  • Decides what enters main

AI can propose and revise work. The repository owner remains responsible for the shared project.

Suggested time: 3 minutes.

Open the relevant lab instructions and point to the repeated workflow. Explain that the configured collaborator may behave more consistently than an open-ended chat, but students still need to review its work.

Takeaways

  • Issues define work that the team can discuss and assign
  • Projects organize issues and pull requests across a larger plan
  • Branches isolate work while it develops
  • Pull requests expose proposed changes for review
  • Reviews can approve, comment, or require revision
  • Merge conflicts pause when Git needs human judgment

Suggested time: 2 minutes.

Return to the opening scenario. Ask one student to explain the sequence they would use now.

Command reference

Goal Command
