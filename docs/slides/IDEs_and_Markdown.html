Today’s question

How can an IDE help us see, create, and manage a data science project?

By the end of class, you should be able to:

  • Explain what an IDE contributes to a project workflow
  • Navigate the core parts of Positron
  • Explain how extensions add capabilities to an IDE
  • Write and preview a useful Markdown document
  • Connect Git concepts from Day 1 to Positron

Suggested time: 2 minutes.

The emphasis today is not replacing the terminal. It is learning how an IDE puts several project tools in one visible workspace.

Review: four places work can live

Location What lives there How work arrives
Local machine Saved changes in working files Save a file
Staged Changes selected for the next commit git add
Version controlled (local) Commits stored in local Git history git commit
Version controlled (GitHub) Commits shared in the remote repository git push

Question to keep asking: Where is my change right now?

Suggested time: 3 minutes.

Clarify that the first three locations are on the local computer. The labels distinguish working files, the staging area, and local Git history. GitHub stores the shared remote history. Trace one change down the table from saving through pushing.

Situation Location

Suggested time: 2 to 3 minutes.

Ask students to answer before revealing each location. The purpose is to reactivate yesterday’s mental model before adding a new interface.

Why use an IDE for data science?

An IDE is a project hub.

Tools in one place

  • File browser
  • Text and code editor
  • Console and terminal
  • Preview and viewer panes
  • Source control and diff viewer
  • Debugging, notebooks, and data tools

Why that matters

  • Less switching between apps
  • Faster feedback while you work
  • Shared context about the project folder
  • Visible feedback about files and errors

Important: The tools still require the same underlying understanding.

Suggested time: 3 minutes.

Keep this broader than Git. Emphasize the repeated data science loop and the value of keeping project context visible.

Positron is a collection of connected tools

Part of Positron What it helps you do
Explorer See the folders and files in a project
Editor Write code, prose, and configuration
Console Work interactively with Python or R
Terminal Run shell commands, Git, and project tools
Viewer Preview Quarto documents and other output
Source Control Inspect, stage, commit, pull, and push changes
Extensions Add support for languages, formats, and workflows

Suggested time: 3 minutes.

Positron is built on Code OSS and adds a layout designed for data science. Point out that the rows provide several views of the same project. Students do not need to use every pane at once.

The project folder

Opening a folder gives Positron context for the active file.

  • The Explorer shows related files and folders
  • The terminal starts in the project folder
  • Git can find the repository and current branch
  • Search and navigation work across the project
  • Quarto can find project settings and website navigation

Daily habit: use File > Open Folder, then work inside the project.

Suggested time: 2 minutes.

Connect this to relative paths and reproducibility. A file rarely makes sense alone. It depends on nearby data, images, code, configuration, and history.

Extensions add capabilities

Extensions are add-ons that teach an IDE about new languages, file types, and workflows.

Type Positron example Capability
Built in Python and R support Consoles, completion, and data science features
Included extension Quarto Preview and render .qmd documents
Included extension Ruff Check and format Python code
Optional extension A language or theme Customize a specific workflow

Suggested time: 3 minutes.

Open the Extensions view from the Activity Bar during the demonstration. Positron includes core extensions and a curated set of bootstrapped extensions. The Quarto extension and Quarto CLI are included, so Positron is ready to preview Quarto documents out of the box.

Extensions deserve judgment

A useful extension should:

  • Solve a real need
  • Come from a publisher you trust
  • Be maintained
  • Fit the workflow you actually use

Too many extensions can:

  • Add clutter
  • Create conflicting behavior
  • Slow startup
  • Expand access to files and network resources

What would you check before installing an extension?

Suggested time: 2 minutes.

Treat extensions like software packages. Show the publisher, update date, repository, and permissions or trust prompt during the live walkthrough.

Why Markdown?

Markdown is plain text with small formatting cues.

A durable format

  • Readable without special software
  • Meaningful line-by-line Git changes
  • Reusable as HTML, slides, reports, or websites

A working format

  • Rendered automatically by GitHub
  • Commonly read and produced by AI chat tools
  • Used for our blogs, website, and final project documentation

Main idea: Simple source can produce polished output.

Suggested time: 3 minutes.

Connect today’s README work to the course website and final project. Markdown is not only a formatting lesson. It becomes a common source language across the semester.

Markdown and AI

When you chat with an AI tool, you already encounter Markdown-like structure:

  • Headings and lists organize a response
  • Code fences preserve code exactly
  • Tables and links make relationships explicit

AI tools can draft, restructure, and clean Markdown because the structure is explicit plain text.

Your role: Decide whether the content is accurate and sounds like you.

Suggested time: 3 minutes.

Show how a structured prompt is easier for both humans and AI to follow. Keep the caution focused on content judgment, not fear of the tool.

Markdown essentials

Goal Markdown
Heading # Heading
Smaller heading ## Smaller heading
Bold **important**
Italic *emphasis*
Bulleted list - item
Numbered list 1. item
Link [label](https://example.com)
Image ![description](images/photo.jpg)
Inline code `git status`
Code block Three backticks before and after the code

Suggested time: 3 minutes.

Demonstrate only the syntax students need for today’s activity. The table is a reference, not a memorization checklist. Remind students to use headings to describe structure rather than only making text larger.

Live walkthrough: one project, many views

The instructor shares the real Positron window. Students open yesterday’s repository and mirror each step.

We will use:

  1. Explorer to locate files
  2. Editor to revise Markdown
  3. Viewer to preview the result
  4. Source Control to inspect and record the change
  5. Terminal to verify what happened

Suggested time: 1 minute to set up, followed by the next three walkthrough slides.

Ask students to arrange their screens so they can see Positron and the projected demonstration. Do not rush past anyone who cannot locate the repository.

Walkthrough 1: orient to the project

Follow along

  1. Select File > Open Folder
  2. Open the repository from Day 1
  3. In Explorer, locate README.md
  4. Open a terminal inside Positron
  5. Run:
pwd
git status

Check: Explorer and pwd identify the same project.

Suggested time: 3 to 4 minutes.

Point to the Activity Bar, Explorer, Editor, Panel, and Status Bar in the real interface. Ask students to name which part of the interface answered each question.

Walkthrough 2: edit and preview Markdown

Follow along

  1. Open README.md in the editor
  2. Add a heading called ## About This Repository
  3. Add one sentence and a three-item list
  4. Save the file
  5. Open a Markdown preview beside the source

What is easier to understand in the source? What is easier to understand in the preview?

Suggested time: 4 minutes.

Use the Command Palette and search for the Markdown preview command if needed. The goal is to practice finding actions, not memorizing every shortcut.

Walkthrough 3: inspect and record the change

Follow along

  1. Open Source Control
  2. Select README.md under Changes and read the diff
  3. Stage the file
  4. Verify with git diff --staged
  5. Enter a specific commit message and commit
  6. Verify with git status

The interface and terminal are two views of the same Git repository.

Suggested time: 5 to 7 minutes.

Pause before staging and ask where the change lives. Pause after staging and ask again. Commit with a message such as Describe repository in README. Push only after the class distinguishes it from commit.

Push, pull, and sync are different

Action Direction Purpose
Push Local to GitHub Send local commits to the remote repository
Pull GitHub to local Bring remote commits into the local repository
Sync Both directions Combine receiving and sending changes

For now: Use Push and Pull separately until you can predict what Sync will do.

Suggested time: 3 minutes.

If the repository has no new remote work, finish the demonstration with Push. Tell students that Sync is useful later, after they can predict both operations.

Activity: begin your About Me page

Your About Me page will become part of your Quarto website.

Write for a visitor who wants to know:

  • Who are you?
  • What are you interested in?
  • What are you learning or building?
  • What should they explore next?

Aim for a clear first draft, not a perfect biography.

Suggested time: 2 minutes to introduce the activity.

This is separate from the guided README demonstration. Students now make individual content and design decisions.

About Me starter

Create about.qmd and place a photo at images/profile.jpg.

---
title: "About Me"
---

# Hello, I am Your Name

![Photo of Your Name](images/profile.jpg)

Write a short introduction here.

## What I am interested in

- One interest
- Something you want to learn

Suggested time: 2 minutes.

Explain that .qmd is a Quarto document whose main writing language is Markdown. The YAML at the top supplies document metadata. The brackets describe the image, while the parentheses contain its relative path. Show students how to place profile.jpg inside an images folder.

About Me activity checklist

Core task

  • Write a short introduction in your own voice
  • Use headings and a list
  • Add one meaningful link
  • Use Quarto: Preview and revise for readability

If you finish early

  • Add an image with useful alternative text
  • Ask AI for a clearer structure, then choose what to keep
  • Inspect the diff, then stage and commit

Final check: Read the rendered page as if you were visiting it for the first time.

What should you remember?

  1. An IDE gathers project tools into one connected workspace.
  2. Opening the project folder gives every tool the right context.
  3. Extensions add capabilities, so choose them intentionally.
  4. Markdown is readable source for humans, Git, GitHub, Quarto, and AI workflows.
  5. Positron represents the same Git locations, but push, pull, and sync remain distinct.

Use the interface for visibility and the terminal for verification.
