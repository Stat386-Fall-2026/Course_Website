Reproducible Publishing with Quarto

From Analysis to a Public Website

STAT 386

Today’s durable question

How can one project communicate a result clearly, preserve the evidence behind it, and stay useful when the data or question changes?

By the end of class, you should be able to:

  • Explain how Quarto connects code, results, visuals, and explanation
  • Distinguish source files, rendered output, and a published website
  • Publish a Quarto website with GitHub Pages
  • Debug a website that does not show the expected update

Suggested time: 1 minute.

Connect this lecture to the previous sequence. Students already have Markdown, Git, GitHub, project environments, and uv. Today those pieces become a publishing workflow.

A familiar request

Your manager gives you data from a regional pilot program.

Compare participation and retention across regions. Recommend where the organization should expand the pilot next.

You have:

  • A CSV with monthly results
  • A notebook for exploring the data
  • A meeting at the end of the week

Suggested time: 1 minute.

Keep the fictional setting simple. The analytical details should remain familiar enough that students can focus on communication and reproducibility.

The first delivery

You complete the analysis:

  1. Run the notebook
  2. Export two figures
  3. Paste them into a document
  4. Write a recommendation
  5. Email the report

The manager receives a readable answer on time.

Suggested time: 1 minute.

Treat this as a reasonable workflow for a first request. Its weaknesses become visible only when the work changes or another person needs to inspect it.

The situation changes

The manager sends an updated CSV and asks for a revised recommendation.

Meanwhile, your teammate notices the surprising increase in West-region retention:

“Does that increase appear among both new and returning participants?”

The work now needs to support three uses:

  • Communicate the result clearly
  • Let a teammate investigate further
  • Update reliably when the data change

Suggested time: 1 to 2 minutes.

Introduce both pressures before asking students to discuss the workflow. Keep the teammate’s question positive. The result sparked useful curiosity rather than distrust.

Design the handoff

What would you hand off so the manager can understand the result, your teammate can investigate it, and you can update it when new data arrive?

What must the project contain? Which pieces must remain connected?

  1. Think: List the minimum pieces the handoff needs.
  2. Pair: Agree on the most important connections.
  3. Share: Name one connection and the failure it prevents.

Suggested time: 4 to 6 minutes.

Give students about 45 seconds to think and 90 seconds to compare answers. During the share, ask each pair for one connection rather than a complete workflow. Listen for links among data, code, figures, explanation, environment information, and versions.

One project supports three needs

Need Entry point What must remain connected
Understand the result Rendered website with visuals and explanation Claims must match the current results
Investigate further Repository with source, code, and data Figures must trace back to their inputs
Update the analysis Reproducible environment and render process New inputs must regenerate the visible output

One project can provide a readable result, an inspectable analysis, and a repeatable update path.

Suggested time: 2 to 3 minutes.

Data science communication uses several forms

Form What it contributes What it cannot provide alone
Data The recorded observations Meaning or interpretation
Code The transformations and calculations A concise explanation for most audiences
Visuals Patterns, comparisons, and uncertainty Complete provenance and context
Text Framing, interpretation, and recommendations Reproducible evidence by itself

The forms become more useful when they remain connected.

Suggested time: 2 minutes.

Emphasize that a figure is often the fastest way to see a pattern, while prose explains why the pattern matters. Code and data let another analyst verify how the figure came to exist.

Copying results creates separate versions

Each handoff can preserve an older result:

  • The notebook may read an earlier file
  • The exported image may come from an earlier run
  • The report may contain a figure that was never replaced
  • The recommendation may describe a result that has changed

Suggested time: 2 minutes.

Do not frame this as carelessness. The workflow asks the analyst to synchronize several separate artifacts manually.

During a full render, the figures and tables come from the code and data in the project.

Generated output reduces ambiguity

When a reader sees a pasted image, they may ask:

  • Which dataset produced this?
  • Which code created it?
  • Does it include the latest observations?

When Quarto generates the image during rendering, the project preserves the path from data to visible result.

The connection depends on rendering the current source. A stale render can still publish an older result.

Preview, render, and publish

Operation What it does Where you inspect the result
uv run quarto preview Renders changes and runs a local preview server Your computer
uv run quarto render Builds the complete static website in docs/ The docs/ folder
Git commit and push Sends source and rendered output to GitHub The repository
GitHub Pages Serves the selected files as a website A public URL

Run a full uv run quarto render before publishing, even after using preview.

Suggested time: 3 minutes.

Preview supports a rapid editing loop. A full render ensures that global settings and all pages have current output.

Source: https://quarto.org/docs/websites/#website-preview Source: https://quarto.org/docs/websites/#website-render

Static publishing

The analysis code runs when Quarto renders the site.

GitHub Pages serves the resulting:

  • HTML pages
  • Stylesheets
  • JavaScript
  • Figures and other site assets

The reader receives the result without installing Python or the project’s packages.

Suggested time: 2 minutes.

Some browser-based interactivity can live inside a static page. Applications that require a continuously running Python process need a server-based host.

Source: https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages

Why .nojekyll exists

GitHub Pages normally assumes that a site published from a branch may need a Jekyll build.

Quarto has already built the website.

An empty .nojekyll file tells GitHub Pages to serve the rendered files without applying another Jekyll build.

The file contains no settings. Its presence is the instruction.

Create it once in the project root and track it with Git.

Suggested time: 2 minutes.

Spell the filename carefully: dot, nojekyll, with no underscore. This file matters for the branch-based publishing workflow used today. Quarto’s GitHub Pages documentation includes it as part of the render-to-docs setup.

Source: https://quarto.org/docs/publishing/github-pages.html#render-to-docs Source: https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site#static-site-generators

Source files and generated files

Item Git decision Reason
.qmd, _quarto.yml, and analysis code Track They define the website and analysis
pyproject.toml and uv.lock Track They support environment reconstruction
Public data used by the site Track when appropriate The analysis needs its inputs
docs/ Track for this deployment method GitHub Pages serves these files
.venv/ and .quarto/ Ignore Tools can regenerate them locally
.env and credentials Ignore and keep private A public repository must not expose secrets

The deployment method makes docs/ a deliberate exception to the usual rule for generated output.

Suggested time: 3 minutes.

Connect this to the earlier discussion of durable inputs and generated outputs. We commit docs here because the chosen Pages configuration consumes that generated directory directly.

Our publishing choice

Today we will publish from the docs/ folder on the main branch:

  1. Quarto renders the site on our computer.
  2. Git records the source and the rendered docs/ files.
  3. GitHub Pages serves the contents of docs/.

This method keeps every stage visible, which makes the workflow easier to understand and debug.

The tradeoff is that we must keep the source and rendered output synchronized.

Suggested time: 2 minutes.

Quarto also supports publishing to a separate gh-pages branch and automated deployment. We use main and docs/ because this exposes the full pipeline and requires no automation. Return to the alternatives later in the semester if useful.

Source: https://quarto.org/docs/publishing/github-pages.html

Live workflow

We will build a small site, add a reproducible analysis, and publish the rendered result.

Suggested time: 1 minute.

Prepare the analysis code and small CSV before class so the demonstration focuses on Quarto rather than pandas syntax.

Demo 1: create and preview the site

quarto create project website USERNAME.github.io
cd USERNAME.github.io
uv init --no-package
uv add jupyter pandas matplotlib
uv run quarto preview

Then inspect:

  • _quarto.yml
  • index.qmd
  • about.qmd
  • The local browser preview

Suggested time: 5 minutes.

Replace USERNAME with the GitHub username used for the demonstration. Keep the generated Quarto scaffold. If setup time is a concern, begin from a prepared copy of this initial state.

Use uv run for preview and rendering so the Python code executes with the packages from the project environment.

Source: https://quarto.org/docs/websites/#quick-start Source: https://docs.astral.sh/uv/concepts/projects/run/

Demo 2: add the analysis page

Create projects/pilot-analysis.qmd with:

  • The manager’s question
  • A code cell that reads data/pilot_results.csv
  • A generated retention figure
  • A short interpretation
  • A proposed next step

Add the page to the site’s navigation, then preview it.

The browser should show the explanation and figure together.

Suggested time: 5 minutes.

Keep the code ready to paste. Show the source beside the rendered result. If possible, fold or hide the code so the page remains accessible to a nontechnical reader.

Demo 3: create and connect the remote

On GitHub, create an empty public repository named:

USERNAME.github.io

Connect the local project:

git branch -M main
git remote add origin https://github.com/USERNAME/USERNAME.github.io.git
git remote -v

Suggested time: 3 minutes.

Create the remote without a README, license, or gitignore because the local project already contains files and Git history. Use the student’s personal account for the eventual portfolio.

Demo 4: render and record the first publication

Create an empty .nojekyll file in the project root.

uv run quarto render
git status
git add .
git commit -m "Publish initial regional pilot analysis"
git push -u origin main

Inspect git status before committing:

  • Source files should show the analysis changes
  • docs/ should show the corresponding rendered changes

Suggested time: 4 minutes.

Pause at git status. Ask students to identify source changes and generated website changes. The commit records the relationship between the two.

Demo 5: configure GitHub Pages

In the repository settings:

  1. Open Pages
  2. Select Deploy from a branch
  3. Select the main branch
  4. Select the /docs folder
  5. Save and open the published URL

For a user site, the URL is:

https://USERNAME.github.io/

Suggested time: 4 minutes plus deployment time.

GitHub may take a few minutes to complete the first deployment. Keep an already-published backup site ready so class time does not depend on deployment speed.

Source: https://quarto.org/docs/publishing/github-pages.html#render-to-docs

Demo 6: a routine data update

Append the latest month to data/pilot_results.csv, then return to the local preview.

git add data/pilot_results.csv projects/pilot-analysis.qmd
git commit -m "Update pilot analysis with latest month"
git push

Open the public website after the new deployment finishes.

Suggested time: 4 minutes.

The local preview should show an updated figure and generated summary. Revise the written recommendation if the new evidence changes the decision.

Deliberately omit the full render before committing. Do not call attention to the omission. The updated source reaches GitHub, but the existing files in docs remain unchanged. This creates the evidence for the think-pair-share on the next slide.

The website still shows the old figure

You observe three facts:

  1. The local preview shows the updated figure.
  2. GitHub contains the updated .qmd source.
  3. The public website still shows the earlier figure.

What do these observations tell you? Where could the update have stopped? What would you inspect first?

Suggested time: 4 to 6 minutes.

Use a full think-pair-share. Give students 30 seconds to reason individually, 90 seconds with a partner, then ask pairs to defend the order in which they would investigate.

Do not reveal that the deliberate mistake was committing and pushing the qmd change without first rendering and committing the updated docs output.

Debugging the publishing pipeline

Check Evidence to inspect What success means
Source Saved .qmd, code, and data The intended change exists locally
Local execution uv run quarto preview The analysis can run and looks correct
Full render Updated files in docs/ The publishable artifact is current
Commit git status and git show Source and output entered Git history
Remote The latest GitHub commit The push reached the remote repository
Deployment Pages deployment status GitHub served the selected branch and folder
Browser Refresh the published URL The reader received the new deployment

Find the last stage that worked, then inspect the next boundary.

Suggested time: 3 minutes.

Walk through the evidence from the prompt. The correct local preview shows that the source can run. The updated source on GitHub shows that a commit and push occurred. Those facts do not prove that docs was rendered or included in the commit.

The missing render

Inspect the repository:

git status
git log --oneline -3

Then repair the update:

uv run quarto render
git add docs
git commit -m "Render updated pilot results"
git push

Confirm that GitHub Pages completes the new deployment.

Suggested time: 3 minutes.

Return to the live site after the deployment completes. Reconnect the corrected public figure to the current data and code.

Takeaways

  1. Data science results need visuals and explanation, while code and data preserve the evidence beneath them.
  2. Quarto generates figures and tables from the analysis during rendering.
  3. Git, GitHub, and uv let a teammate reconstruct and extend the project.
  4. GitHub Pages gives nontechnical readers a browser-based result.
  5. Debugging begins by locating the last successful stage in the publishing pipeline.
  6. The same workflow can support every blog and project added to the portfolio.
