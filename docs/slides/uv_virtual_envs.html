Reproducible Python Projects

Virtual Environments, Dependencies, and uv

STAT 386

Today’s durable question

What information lets another computer recreate the environment that made your analysis work?

By the end of class, you should be able to:

  • Explain the problems solved by project environments and dependency management
  • Distinguish a dependency manifest, a lockfile, and an installed environment
  • Translate a general reproducible workflow into uv commands
  • Share a version-controlled project that another person can reconstruct

Suggested time: 1 minute.

Tell students that uv supplies today’s commands, but the underlying ideas apply across languages and tools. A future tool may change the syntax without changing the problems that the workflow must solve.

Think, pair, share: one project changes another

Day What happened?
Monday Project A runs correctly with dplyr
Tuesday You update dplyr while working on Project B
Wednesday Project A behaves differently, although none of its files changed

How could work in Project B affect Project A? What important information lived outside Project A’s files? What would prevent this connection?

Suggested time: 3 minutes.

Give students 30 seconds to think, one minute to discuss, and one minute to share. Ask one pair to explain the mechanism and another pair to propose a prevention strategy.

Listen for a shared user library, a changed package version, missing environment information, and project-specific isolation. If needed, show .libPaths() after the discussion to reveal where R searches for installed packages.

Source: https://stat.ethz.ch/R-manual/R-devel/library/base/html/libPaths.html

Why R can make the problem less visible

Observation What it means
R projects often search the same user library Updating a package can affect several projects
Project A’s files did not change Part of its computational state lived outside the project
A private project library separates installed packages Changes in one project stay contained
A lockfile records the selected versions A collaborator can reconstruct the resolution later
R with renv Python with uv Purpose
Project library .venv/ Local packages for one project
renv.lock uv.lock Recorded dependency resolution
renv::restore() uv sync Reconstruct the local environment

Suggested time: 2 minutes.

Use this slide to close the discussion. R and Python face the same dependency problem. Introductory R workflows often share a package library, so the environment stays in the background. renv makes project isolation and reconstruction explicit, much like uv in today’s Python workflow.

Source: https://rstudio.github.io/renv/

Four jobs behind a reproducible environment

Job Question it answers
Isolation Can this project change without disturbing another project?
Declaration Which packages does the project’s code directly require?
Resolution Which complete set of package versions works together?
Reconstruction Can another computer install a compatible environment?

A virtual environment handles isolation. Dependency metadata and a lockfile make reconstruction possible.

Suggested time: 2 minutes.

Keep the four jobs distinct. A .venv with undocumented packages provides isolation but remains difficult to reproduce. A package list without isolation can still let projects interfere with one another.

Intent, resolution, and local installation

Layer Python example Human or generated?
Intent pyproject.toml Human-readable project declaration
Resolution uv.lock Tool-generated exact dependency graph
Local installation .venv/ Generated files on one computer

Suggested time: 2 minutes.

Emphasize the direction. The manifest describes the project’s needs. A resolver chooses a complete compatible set. The package manager installs that resolution into a local environment.

The installed environment is an output of the process rather than the source of truth.

Direct and transitive dependencies

Your code may directly require one package:

main.py imports pandas

That package may require several others:

pandas depends on NumPy and other packages
Dependency Who chose it? Where is it recorded?
Direct Project author Manifest and lockfile
Transitive Dependency resolver Lockfile

The lockfile records the complete dependency graph, including packages your code never imports directly.

Suggested time: 2 minutes.

This explains why a lockfile contains more package names than the student added. The author declares direct needs. The resolver computes a full compatible graph.

Think, pair, share: what belongs in Git?

Suppose a project contains:

.python-version     pyproject.toml     uv.lock
main.py             .venv/             __pycache__/

Sort the items into two groups: durable project inputs and locally generated outputs. Which items should Git track, and why?

Suggested time: 3 minutes.

Give pairs one minute to sort the files, then ask two pairs to justify one disputed item. Press for a general rule rather than a memorized list.

Expected distinction: another computer needs the Python requirement, manifest, lockfile, and code as inputs. The environment and caches can be regenerated locally.

Git stores the reconstruction inputs

Item Role Git decision
.python-version Records the intended Python version Commit
pyproject.toml Declares direct dependencies and settings Commit
uv.lock Records the complete dependency resolution Commit
main.py and other project files Define the analysis Commit
.venv/ Stores one local installation Ignore
__pycache__/ Stores disposable Python cache files Ignore

Version-control the files another computer needs as inputs. Ignore files the project tools can regenerate.

Suggested time: 2 minutes.

Use this slide to summarize the discussion. The repository preserves the recipe and the analysis. The package manager builds a local installation from those tracked inputs.

Think, pair, share: enough information to reproduce?

A collaborator receives one of these bundles:

Bundle Contents
A Code only
B Code and somebody else’s .venv/
C Code and a dependency manifest
D Code, Python requirement, manifest, and lockfile

Rank the bundles from least to most useful for reproducibility and later debugging.

Be ready to defend your ranking using portability, recorded environment information, and what could still change. Which comparison was hardest?

Suggested time: 4 minutes.

Think for 30 seconds, discuss for 90 seconds, then ask two pairs with different rankings to defend their choices. Give the second pair a chance to respond to the first.

The comparison between B and C should produce useful disagreement. Bundle B contains more installed files, but those files may depend on the original operating system, architecture, and paths. Bundle C is portable but may resolve to different package versions later.

Ranking debrief: the strongest project contract

Bundle What it provides Main limitation
A: code only The analysis logic No environment information
B: code and .venv/ One installed environment Generated files may not transfer across computers
C: code and manifest Portable dependency intent A later resolution may select different versions
D: code, Python requirement, manifest, and lockfile Intent plus the exact dependency resolution Does not capture every operating-system or hardware difference

Bundle D gives the strongest project-level basis for reconstruction and debugging.

Suggested time: 2 minutes.

Use this slide to settle the ranking. A reasonable pair may place B above C for immediate forensics on a compatible machine, but C usually transfers more cleanly. D combines portable project inputs with a recorded resolution.

A tool-independent workflow

Any replacement for uv must still help with these operations.

Learn the purpose of each operation first. Command syntax becomes a translation exercise.

Suggested time: 2 minutes.

Read the workflow using generic verbs. Ask students which steps they have already encountered in R, even if the tools hid them.

The general workflow in uv

General operation uv project representation
Record the Python version .python-version
Create project isolation .venv/
Declare direct dependencies pyproject.toml and uv add
Record the exact resolution uv.lock
Reconstruct local packages uv sync
Run inside the environment uv run

Other tools use different commands and filenames while performing similar jobs.

Suggested time: 2 minutes.

This is the bridge from theory to the command-line toolbox. Students should be able to replace the right column later without discarding the left column.

Live workflow: author and reproducer

We will build a project on one computer and reconstruct it from a fresh clone on another.

Author: initialize, add, run, commit, and share
Reproducer: clone, sync, and run

Suggested time: 1 minute.

The class follows the author steps from an empty folder. Create the GitHub repository during the demo. Choose a student reproducer before starting and confirm that the student can access GitHub and has Git and uv installed.

For a 50-minute class, everyone can follow the local author steps while the instructor or one assigned pair creates and pushes the shared repository. One student then clones it on a different computer.

Author 1: initialize the project

cd ~/Desktop/School/STAT_386
uv init --no-package environment-demo
cd environment-demo
ls -la

Look for:

.git/              .python-version
.gitignore         main.py
README.md          pyproject.toml

Check: pwd ends in environment-demo, and git status recognizes a repository.

Suggested time: 2 minutes.

Adapt the first path to the course folder students created earlier. --no-package creates a flat application project suited to a small data analysis.

Point out that uv init created both the project files and the local Git repository. .venv/ and uv.lock will appear when the project first resolves and installs dependencies.

Source: https://docs.astral.sh/uv/concepts/projects/init/

Author 2: create and connect the remote

On GitHub, create a new repository named environment-demo:

  • Choose Public, or give the student reproducer access to a private repository
  • Leave README, .gitignore, and license initialization unchecked
  • Create the repository and copy its URL

Connect the local repository:

git branch -M main
git remote add origin REPOSITORY_URL
git remote -v

Check: git remote -v shows the GitHub URL for origin.

Suggested time: 3 minutes.

Create the remote during class so students see that the local Git repository and the GitHub repository begin as separate objects. Leaving the remote empty avoids a competing first commit.

Students must already have GitHub authentication configured for the later push. If every student creates a remote, circulate while they copy their URLs. For a tighter demo, create one class remote while everyone connects conceptually.

Source: https://docs.github.com/en/migrations/importing-source-code/using-the-command-line-to-import-source-code/adding-locally-hosted-code-to-github

Author 3: add a dependency and run code

uv add pandas

Replace main.py with:

import pandas as pd

scores = pd.DataFrame(
    {
        "section": ["A", "A", "B", "B"],
        "score": [82, 94, 88, 92],
    }
)

print(scores.groupby("section")["score"].mean())
uv run python main.py

Suggested time: 4 minutes.

Prepare the Python code for copy and paste. uv add declares pandas in the manifest, resolves and records the dependency graph, and installs the resolved packages into .venv/.

uv run executes inside the project environment. Ask which installed copy of pandas the script imports.

Source: https://docs.astral.sh/uv/reference/cli/#uv-add Source: https://docs.astral.sh/uv/concepts/projects/run/

The theory becomes visible

git status
uv tree
uv run python -c "import sys; print(sys.executable)"
Observation Concept
.venv/ now exists Local isolation and installation
pyproject.toml lists pandas Direct dependency declaration
uv.lock contains more packages Complete dependency resolution
Python path points inside .venv Code runs in the project environment

Suggested time: 2 minutes.

Open pyproject.toml and locate the direct dependency. Open uv.lock only long enough to show exact versions and transitive dependencies. Use uv tree to make the dependency graph easier to read.

In Positron, select the interpreter inside .venv so editor execution uses the same environment.

Author 4: commit and share the specification

git status
git diff
git add .
git diff --staged
git commit -m "Create reproducible score summary"
git push -u origin main

Before committing, verify that Git includes:

.gitignore          main.py
.python-version     pyproject.toml
README.md           uv.lock

Git should ignore .venv/.

Suggested time: 3 minutes.

Connect every tracked file to the earlier theory. Inspect .gitignore and confirm the .venv rule. git add . is appropriate here only after reviewing git status and the diff.

After the push, open the GitHub repository and verify that pyproject.toml and uv.lock appear while .venv/ does not. The remote receives the code and reconstruction inputs rather than the author’s installed environment.

Predict before uv sync

The reproducer is about to clone the project on a different computer.

Before running anything, predict:

  1. Which project files will arrive through Git?
  2. Will .venv/ already exist?
  3. What must uv sync read and create?
  4. Which file should remain unchanged during synchronization?

Suggested time: 2 minutes.

Give pairs one minute. Expected answers: Git brings the tracked code and specification, .venv is absent, uv sync reads the Python requirement, manifest, and lockfile, then creates the local environment. When the manifest and lockfile already agree, synchronization should not need to change the lockfile.

Student reproducer: clone, sync, and run

cd ~/Desktop/School/STAT_386
git clone REPOSITORY_URL
cd environment-demo
ls -la

Confirm that .venv/ is absent, then run:

uv sync
uv run python main.py
uv run python -c "import sys; print(sys.executable)"

The environment-setup step on the second computer is uv sync.

Suggested time: 4 minutes.

Have the selected student clone on a different computer and share the terminal output. If the author and reproducer roles must happen on one computer, clone into environment-demo-copy instead.

After uv sync, show that .venv/ now exists, the program produces the same summary, and the interpreter path points inside the student’s project. uv run also checks synchronization automatically, but use explicit uv sync today so students can see the reconstruction step.

Source: https://docs.astral.sh/uv/concepts/projects/sync/

Reconstruction rather than copying

The author and reproducer now have:

  • The same tracked code
  • The same declared dependencies
  • The same locked dependency resolution
  • Different locally generated .venv/ directories

The tracked specification had to match. Each computer generated its own local environment from that specification.

Suggested time: 2 minutes.

This is the main conceptual payoff. Ask a student to name what Git transferred and what uv sync constructed. The two .venv directories do not need to be copied or byte-for-byte identical. The repository supplies a shared specification from which each machine builds a compatible local environment.

Natural stopping point for a 50-minute class. Continue to extended practice if time remains or begin here next time.

Extended practice: the project evolves

Adding a library changes the project specification, so the author and reproducer repeat the same cycle.

Author: add, change, run, commit, push
Reproducer: pull, sync, run

Optional extension: 8 to 12 minutes.

Use this section if the core workflow finishes early. It can also open the next meeting as retrieval practice.

Extended practice 1: add tabulate

On the author’s copy:

Predict which tracked files and which local-only directory will change.

uv add tabulate

Replace the final line of main.py with:

summary = scores.groupby("section", as_index=False)["score"].mean()
print(summary.to_markdown(index=False))

Then run and share the update:

uv run python main.py
git status
git diff
git add .
git diff --staged
git commit -m "Print summary as a Markdown table"
git push

Suggested time: 4 to 6 minutes.

Before running uv add, ask students which tracked files they expect to change. Expected answers: pyproject.toml, uv.lock, and then main.py after editing. .venv/ also changes locally but remains ignored.

Extended practice 2: reproduce the update

On the reproducer’s copy:

git pull
uv sync
uv run python main.py

Verify:

  • git pull retrieves the changed code and project specification
  • uv sync installs the new dependency into the local .venv/
  • The program prints a Markdown table

What stayed the same about the workflow even though the code and dependencies changed?

Suggested time: 4 to 6 minutes.

The durable cycle remains unchanged: update the specification, share it through version control, reconstruct locally, and run inside the environment.

A short diagnostic routine

Symptom First question Likely action
Project metadata cannot be found Am I in the project directory? cd to pyproject.toml
Import fails in the terminal Does the environment match the lockfile? Run uv sync, then uv run
Import fails only in Positron Which interpreter did Positron select? Choose the interpreter inside .venv
A package works only for the author Did the author declare and commit it? Use uv add, then commit the manifest and lockfile

Check location, project specification, synchronization, and interpreter selection.

Suggested time: 2 minutes.

Walk through one example. If uv run works but Positron shows a missing import, the project environment probably works while Positron points to another interpreter.

If the tool changes

Suppose a future course uses a different environment manager.

Ask the new tool how to:

  1. Create project isolation
  2. Declare direct dependencies
  3. Resolve and lock the full dependency graph
  4. Reconstruct the environment from tracked files
  5. Run code inside that environment

The commands may change. The questions and responsibilities remain recognizable.

Suggested time: 2 minutes.

Return directly to the desired durable outcome. Students should leave with a checklist for evaluating or learning the next tool rather than treating uv commands as isolated facts.

Takeaways

  1. R and Python both face dependency conflicts.
  2. Isolation prevents projects from changing one another’s installed packages.
  3. A manifest records direct needs, while a lockfile records the complete resolution.
  4. Git shares the code and project specification while the environment remains local.
  5. A collaborator reconstructs the environment rather than receiving somebody else’s installation.
  6. uv provides a small toolbox for this general workflow.

Suggested time: 1 minute.

Ask students to explain the fifth point in their own words. That explanation reveals whether they understand the purpose behind uv sync.
