IDEs and Virtual Environments for Data Science

VS Code + uv

What You Should Be Able to Do After Today

By the end of class, you should be able to:

  • Explain what an IDE gives you (and what it does not)
  • Explain what a virtual environment is and why teams rely on them
  • Use VS Code for the everyday loop: edit, run, debug, version control
  • Use uv to create a project, add dependencies, reproduce an environment
  • Resolve a merge conflict using VS Code’s merge UI

Two Recurring Problems in Real Projects

Productivity problem

  • You need a fast edit-run-check loop
  • Fewer context switches
  • Help from tooling

Reproducibility problem

  • “It works on my machine” is not a plan
  • Different projects need different versions
  • Teams need reliable setup

Key idea: An IDE addresses productivity; a virtual environment addresses reproducibility. You need both.

Why Use an IDE for Data Science?

An IDE is a hub.

  • Editor + terminal + debugger + notebooks + Git in one place
  • Faster feedback, fewer context switches
  • Project-level settings

Trade-offs: learning curve, extensions can sprawl, heavier than a bare text editor.

IDE Landscape (Quick Take)

  • VS Code / Code-OSS: huge ecosystem; strong Git, Python, notebook support
  • PyCharm: excellent Python refactoring; heavier
  • JupyterLab: notebook-first; great for EDA; weaker as project hub
  • RStudio / Positron: strong for R and Quarto
  • Terminal + Vim/Neovim: light and powerful; steep curve

VS Code Mental Model

  • A project is a folder (workspace) plus settings
  • Views: Explorer, Editor, Terminal, Source Control, Extensions
  • The Command Palette is your “search bar” for actions

Key idea: Think “open a folder,” not “open a file.” Settings travel with the project.

VS Code: The 90% You Use All the Time

Daily moves

  • Open folder: File > Open Folder
  • Integrated terminal: Terminal > New Terminal
  • Command Palette: Cmd/Ctrl+Shift+P
  • Search files: Cmd/Ctrl+P

Two habits

  • Keep work inside a project folder
  • Let the project choose its Python interpreter

Tip: Cmd/Ctrl+P jumps to files; Cmd/Ctrl+Shift+P runs commands. Different shortcuts, both essential.

Extensions We Will Use

Quarto in VS Code

With the Quarto extension, you can preview .qmd inside VS Code.

touch report.qmd
quarto render report.qmd

In VS Code: run the command Quarto: Preview.

Demo flow: create report.qmd → add a heading and a code cell → Preview in viewer pane → edit and watch it update.

Git Inside VS Code

Same concepts as terminal Git.

  • Source Control view shows: changed files, staged files, diffs
  • Stage changes, write commit message, commit
  • Push and pull without leaving the editor

Key idea: The UI is a thin layer over Git. Nothing the buttons do is hidden from the terminal.

CLI to VS Code Mapping

Terminal Git VS Code UI
git status Open Source Control view
git add <file> + to stage files
git commit -m "msg" Type message, click Commit
git push Sync / Push from UI
git pull Pull from UI

Tip: The Source Control view badge number shows how many files have changed.

Merge Conflicts: What They Are

A conflict happens when Git cannot automatically combine two sets of changes.

  • Most common: two branches edit the same lines
  • Git stops and asks you to decide

Note: Conflicts are not errors — they are Git being careful. You resolve them by choosing which changes win.

Conflict Resolution in VS Code

Markers in the file:

<<<<<<< current branch
your changes
=======
incoming changes
>>>>>>> incoming branch
  • VS Code adds inline actions: Accept Current, Accept Incoming, Accept Both, Compare changes, 3-way merge editor
  • After resolving: save file, stage it, commit the merge resolution

Why Virtual Environments Exist

Python projects depend on external packages. Packages depend on other packages.

If everything lives in one global Python:

  • Projects fight over versions
  • Upgrading one package breaks another
  • Reproducing an environment is hard

Key idea: A virtual environment isolates dependencies per project so each project gets exactly the versions it needs.

What Is a Virtual Environment?

An isolated folder containing:

  • A Python interpreter
  • Installed packages (site-packages)
  • Scripts (python, pip, pytest)

Rule of thumb: one environment per project. Create it fresh, ignore it in Git, recreate it from the lockfile.

Why uv for This Class

uv is a fast, standards-first tool.

  • uv init — creating projects
  • uv add / uv remove — managing dependencies
  • uv sync — syncing environments
  • uv run — running code
  • uv.lock — lockfile for reproducibility
  • Manages Python versions too

uv Project Structure (What to Commit)

Commit: pyproject.toml, uv.lock, .python-version

Do NOT commit: .venv/ (local environment)

myproject/
  pyproject.toml
  uv.lock
  .python-version
  .venv/   # ignore in git

Note: Add .venv/ to .gitignore. The environment is local; the lockfile is shared.

uv: The Commands You’ll Use Most

uv init myproject
cd myproject
uv add httpx rich
uv sync
uv run python main.py

What happens: uv init scaffolds the project, uv add updates pyproject.toml and uv.lock, uv sync builds .venv, and uv run executes inside that environment.

VS Code + uv: How They Fit Together

  • uv manages dependencies and environment in .venv
  • VS Code uses that environment as the interpreter

Two stable habits

  • Run scripts with uv run ... in the terminal
  • In VS Code, select the interpreter inside .venv

Tip: Cmd/Ctrl+Shift+P → Python: Select Interpreter → pick the .venv path. VS Code remembers it per project.

In-Class Demo Outline

  1. Create a new project: uv init, add a dependency, run a script
  2. Open folder in VS Code, select the interpreter
  3. Install Quarto extension, preview a .qmd
  4. Initialize Git, commit from Source Control, push
  5. Create and resolve a conflict

Pace: ~2 minutes per step. Narrate each action; students follow along on their machines.

Exercise 1 (pairs): Build and Run a uv Project

Goal: build muscle memory for uv init, uv add, uv run.

Checklist

  1. uv init joke-demo
  2. uv add httpx
  3. Write a script that calls icanhazdadjoke.com
  4. Run with uv run python main.py
  5. Commit pyproject.toml, uv.lock, and the script

Check: uv run prints a dad joke; git status shows a clean tree after the commit.

Exercise 2 (pairs): Resolve a Merge Conflict in VS Code

Goal: get comfortable with the merge UI.

  1. Each person makes a branch and edits the same line in README.md
  2. Merge one branch first
  3. Merge the second branch and resolve the conflict in VS Code
  4. Stage, commit, push, then pull to verify

Check: both teammates’ edits are visible in README.md; git log shows the merge commit.

Optional 5-Minute Repo Tour: scikit-learn

Look for these signals of a healthy project:

  • Clear README
  • Automated checks (CI)
  • Code quality tools
  • Central config in pyproject.toml
  • Tests and docs alongside code

Tip: Skim pyproject.toml first — it tells you how the project is built, tested, and tooled.

Wrap-Up: What to Remember

  • IDEs reduce friction in the edit-run-check loop
  • Virtual environments prevent dependency conflicts and enable reproducibility
  • VS Code: editor + terminal + Git + extensions
  • uv: project files (pyproject.toml, uv.lock, .python-version) plus local .venv
  • Use uv sync after pulling; use uv run to run reliably
