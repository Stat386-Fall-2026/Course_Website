Importing and Loading Data

Turning stored values into trustworthy DataFrames

Loading is an act of interpretation

Stored source

A file contains bytes arranged according to a format.

Reader settings

A function decides where rows begin, what separates columns, and how values should be typed.

DataFrame

pandas builds an in-memory table that reflects those decisions.

Two analysts can read the same file and produce different DataFrames.

Common representations

Stored representation What it preserves pandas reader
CSV or TSV Plain text arranged in rows and fields read_csv()
Excel workbook Sheets, cells, and some cell types read_excel()
JSON Objects, arrays, and nested structure read_json()
Parquet Column types and compressed columnar data read_parquet()

The reader often accepts either a file path or a URL.

CSV receives the most attention today. Mention that APIs and databases come later in the course.

Conceptual check: one CSV row

talk_id,title,views
0017,"Data, Decisions, and You","12,450"

Discuss with a neighbor:

  1. How many columns should pandas create?
  2. Why do two values use quotation marks?
  3. Which pandas types should the columns have?

The row contains three fields. Quotation marks protect commas inside a field. talk_id should remain text, while views should eventually become numeric.

Files store representations

The text 0017 can represent several ideas:

  • The quantity seventeen
  • A four-character identifier
  • A code whose leading zeros carry meaning

The characters alone do not tell pandas which meaning applies.

Variable meaning should guide the import settings.

Reproducible paths with pathlib

Inside a Python script:

from pathlib import Path

PROJECT_ROOT = Path(__file__).resolve().parents[1]
DATA_DIR = PROJECT_ROOT / "data"

talks = pd.read_csv(DATA_DIR / "talks.csv")

Inside a notebook or Quarto document launched from the project root:

talks = pd.read_csv("data/talks.csv")

The exact starting point depends on how the code runs. Confirm the working directory when a relative path surprises you.

A file’s schema

A schema describes how stored values map to variables.

Question Example decision
What separates fields? Comma, tab, or semicolon
Where are the column names? First row or a separate data dictionary
Which codes mean missing? NA, Unknown, or -999
Which type fits each variable? String, integer, date, or Boolean

CSV files rarely carry a complete schema with them.

Import options express the schema

talks = pd.read_csv(
    "data/talks.csv",
    sep=",",
    dtype={"talk_id": "string"},
    parse_dates=["published_date"],
    na_values=["Unknown", "Not reported"],
)

You rarely need every option at once. Use the options that express what you know about the source.

Type inference begins with observed values

talk_id  views
00017    12450
00018    8905
00019    Not reported

pandas sees patterns in the stored values. It cannot know the full meaning of a variable.

  • talk_id looks numeric, so leading zeros may disappear.
  • views contains text, so the entire column may remain text.

Conceptual check: number or label?

How should each value enter a DataFrame?

Value Possible meaning
00124 Student ID
84653 ZIP code
2026 Calendar year
4.7 Rating
12% Response rate

IDs and ZIP codes are labels. Rating is quantitative. Year depends on the analysis. A stored percentage usually needs cleaning before arithmetic.

Missing values have source-specific codes

82
NA
-999
Not reported
0

Which entries might mean missing? Which entry requires the most context?

NA, -999, and Not reported often encode missingness. Zero may be a real measurement or a missing-value code. The source documentation should decide.

Later we will study why values are missing. Today we focus on representing missingness correctly during import.

Conceptual check: which date?

03/04/2026

What date does this represent?

It could mean March 4 or April 3. Valid text can still carry ambiguous meaning.

A first-response routine

Immediately after loading, ask:

  1. Did I get the expected rows and columns?
  2. Do the names and values line up?
  3. Did identifiers retain their original form?
  4. Do the data types match the variables?
  5. Did pandas recognize missing values?
  6. Do basic ranges and relationships look plausible?

Inspection tools answer different questions

talks.head()           # What do the first records look like?
talks.shape            # How many rows and columns loaded?
talks.columns          # Which names did pandas recover?
talks.dtypes           # How did pandas represent each column?
talks.info()           # Which columns contain missing values?
talks.isna().sum()     # Where are missing values concentrated?

No single method proves that the import is correct.

Conceptual check: one column instead of five

You expect five columns, but pandas reports:

data.shape
# (500, 1)

The code produced a DataFrame without raising an exception.

What probably happened, and what would you inspect next?

The reader probably used the wrong delimiter. Inspect the raw file and its first few lines.

Hard and silent failures

Hard failure

FileNotFoundError

The program stops and points toward a problem.

Silent failure

shape: (500, 1)

The program continues with an incorrectly interpreted table.

Silent failures can survive long enough to affect an analysis.

Conceptual check: rank the warning signs

Rank these from most obvious to easiest to miss. Then rank them by potential harm.

  1. Python raises FileNotFoundError.
  2. A date column has type object.
  3. A five-column file loads as one column.
  4. An identifier loses its leading zeros.

There is no required ranking. Defend it by separating visibility from downstream consequences.

Demo: explicit import decisions

talks = pd.read_csv(
    DATA_DIR / "talks.csv",
    dtype={"talk_id": "string", "views": "string"},
    parse_dates=["published_date"],
    na_values={
        "views": ["Not reported"],
        "rating": ["Unknown"],
    },
    true_values=["Yes"],
    false_values=["No"],
)

Each option follows from the variable meaning or source documentation.

Demo: cleaning after import

talks["views"] = pd.to_numeric(
    talks["views"].str.replace(",", "", regex=False)
).astype("Int64")

Some decisions fit naturally in the reader. Other representations are clearer to transform after loading.

Int64 is pandas’ nullable integer type, so the column can contain both integers and missing values.

Demo: validation makes expectations executable

assert talks.shape == (12, 9)
assert talks["talk_id"].str.fullmatch(r"\d{5}").all()
assert talks["talk_id"].is_unique
assert talks["published_date"].dtype.kind == "M"
assert talks["views"].dropna().ge(0).all()

The final assertion fails because one talk has -150 views.

Should we replace it, delete the row, or do something else?

Suspicious data requires judgment

suspicious_rows = talks.loc[talks["views"].lt(0)]

We know the value violates a reasonable expectation. We do not know the correct value.

talks.loc[talks["views"].lt(0), "views"] = pd.NA

Marking the value as missing preserves the record and avoids inventing a correction. The analyst should also document the issue and verify the source.

Before analysis begins

Describe the interpretation

  • Source and file format
  • Path and delimiter
  • Types, dates, and missing-value codes

Support it with evidence

  • Expected shape and column names
  • Plausible values and relationships
  • Assertions for important assumptions

A successful reader call starts the import. Inspection and validation establish whether the result deserves trust.
