Why Do We Join Data?

It’s rare to have a single “master” dataset. Data lives in:

  • Separate tables — transactions vs customers vs products
  • Separate sources — API + scraped + local
  • Different grains — daily vs monthly, county vs state

Joining constructs analysis-ready datasets.

A Mental Model: Tables Are Lego Bricks

  • Each table is a brick with a purpose
  • Keys are the studs and sockets

Good joining is:

  • Knowing which keys should match
  • Confirming how many matches you expect
  • Checking who got dropped and why

The Workhorse: pd.merge

pd.merge(left, right, how=..., on=...)

Think “SQL join” but in pandas. Key params:

  • how — "inner", "left", "right", "outer"
  • on / left_on / right_on
  • validate — cardinality check
  • indicator — track merge results

Inner Join

Keeps rows with keys found in BOTH tables.

Good when analysis requires matched records and you expect near-perfect coverage.

pd.merge(a, b, how="inner", on="id")

Left Join

Keeps all rows from the left table. Adds columns from the right when keys match. Unmatched keys become NaN.

pd.merge(orders, customers,
         how="left", on="customer_id")

Right Join

Keeps all rows from the right table. Mostly symmetric with left join — just swap table order.

pd.merge(a, b, how="right", on="id")

Outer Join

Keeps rows whose keys appear in EITHER table. Useful for a “union of coverage.” Often requires follow-up cleaning.

pd.merge(a, b, how="outer", on="id")

Quick Reference: Join Types

inner

Matched keys only

Strict matching

left

All left + matches

Enrich a “main” table

right

All right + matches

Same, but right is “main”

outer

All keys from both

Coverage comparisons / audits

Keys: What You Join On

Keys should represent the same real-world thing in both tables.

Clean keys before merging:

  • Consistent types (string vs int)
  • Consistent formats (zero padding, casing, whitespace)
  • Consistent meaning

Tip: Mismatched key types are the #1 cause of silent missing matches.

Duplicates and Cardinality

A merge can explode rows if keys are duplicated.

  • one-to-one — one row matches one row
  • one-to-many — e.g., one customer, many transactions
  • many-to-many — danger zone (row multiplication)

Always check row counts before and after a merge.

Use validate= to Sanity-Check Joins

pd.merge(customers, demographics,
         on="customer_id", how="left",
         validate="one_to_one")

Options: "one_to_one", "one_to_many", "many_to_one", "many_to_many"

If validate fails, you have unexpected duplicates. Fix them before trusting the join.

Use indicator= to See What Matched

m = pd.merge(a, b, on="id", how="outer", indicator=True)
m["_merge"].value_counts()
  • both — matched
  • left_only — missing from right
  • right_only — missing from left

Joining on Indexes

customers = customers.set_index("customer_id")
orders    = orders.set_index("customer_id")

orders.join(customers, how="left")

.join() defaults to joining on the index — handy when the index already encodes your key.

When Is Index-Joining Useful?

  • Time series indexed by date
  • Panel data indexed by (id, date)
  • When you want a clear “primary key” structure

Problem: Different Time Intervals

Daily data (stock prices, weather) vs monthly data (unemployment, CPI).

A direct merge on date often fails because the keys don’t align — there’s no row for the 15th in a monthly table.

Strategies for Time Interval Mismatch

Align to a common period:

  • Convert daily → monthly (aggregate)
  • Expand monthly → daily (forward-fill)

Use merge_asof for “nearest previous” matches:

pd.merge_asof(
    daily.sort_values("date"),
    monthly.sort_values("date"),
    on="date", direction="backward"
)

Problem: Different Geographic Levels

County-level outcomes vs state-level policies.

A join requires:

  • A crosswalk (county → state)
  • Consistent identifiers (FIPS codes, abbreviations)
  • Sometimes aggregation

Strategies for Geographic Mismatch

Enrich

Add state info to county rows (many-to-one).

Aggregate

Roll counties up to state, then join.

Disaggregate carefully — going state → county requires assumptions or weights.

pd.concat vs merge

merge

Combines columns using key matches (relational join).

pd.merge(left, right,
         on="id", how="left")

concat

Stacks dataframes along rows or columns.

# stack rows (same columns)
all_months = pd.concat(
    list_of_monthly_dfs,
    ignore_index=True)

# stack columns (same index)
wide = pd.concat(
    [left.set_index("id"),
     right.set_index("id")],
    axis=1)

Multi-Key Joins

Many real joins need multiple keys: (state, year), (customer_id, order_date).

pd.merge(a, b, how="left",
         on=["state", "year"])

A Join Checklist

  1. Identify the unit of observation (grain) for each table
  2. Define join keys and clean them
  3. Decide which table is “main” (often a left join)
  4. Validate expected cardinality (validate=)
  5. Audit match quality (indicator= and summary checks)
  6. After join: check row counts, missingness, duplicates

Common Pitfalls

  • Row multiplication from many-to-many joins
  • Dirty keys — leading zeros, spacing, type mismatch
  • Silent missing matches — different naming conventions
  • Wrong grain — county vs state, day vs month
  • Forgetting to check what got dropped in an inner join

Project Tie-In

Your final project dataset will likely require:

  • Multiple API calls
  • Scraping multiple pages
  • Multiple non-trivial joins

Treat joining as part of data documentation:

  • What keys did you use?
  • What fraction matched?
  • What assumptions aligned the grains?

Wrap-Up

  • pd.merge handles most joins cleanly
  • Use validate and indicator to avoid surprises
  • For mismatched grains: resample/aggregate, merge_asof, crosswalks
